# Стратегии расширяемости (Escape Hatches)

Когда в Core API не хватает методов, разработчики плагинов оказываются в тупике. Чтобы дать им "бесконечную гибкость", нужно предоставить способы обхода ограничений ("escape hatches"). Вот основные подходы, от безопасных к самым мощным.

## 1. Доступ к "Движку" (The Engine Access) - 🏆 Рекомендуемый

Самый эффективный способ — дать доступ к экземплярам библиотек, на которых построен проект. В нашем случае это **CodeMirror** (редактор) и **React** (UI).

**Как это работает:**
Вместо того чтобы писать обертки для каждого метода CodeMirror (`insertText`, `replaceSelection`, `getLine`, `addCursor`...), мы просто отдаем сам объект редактора.

```typescript
// В API
interface EditorApi {
    // ... стандартные методы ...
    
    /**
     * Прямой доступ к инстансу CodeMirror EditorView.
     * @warning Использование этого свойства может сломать совместимость в будущих версиях.
     */
    unsafe_getCodeMirror(): EditorView | null;
}
```

**Плюсы:**
*   ➕ **Нулевые усилия со стороны Core:** Не нужно писать прокси-методы. Достаточно отдать ссылку.
*   ➕ **Бесконечные возможности:** Плагин может использовать *любую* фичу CodeMirror, даже ту, о которой вы не знали.
*   ➕ **Документация уже есть:** Разработчики читают доки CodeMirror, а не Notehub.

**Минусы:**
*   ➖ Если вы смените CodeMirror на Monaco, все плагины сломаются.

## 2. Namespace "Unsafe" или "Internal"

Группировка всех внутренних API в отдельный неймспейс, чтобы разработчик понимал риски.

```typescript
ctx.unsafe.app // Доступ к корневому классу приложения
ctx.unsafe.window // Доступ к окну (если в сендбоксе)
ctx.unsafe.fs // Прямой доступ к Node/Tauri FS без проверок
```

Это подход Obsidian (`app.internal...`). Это позволяет хакать систему, но явно помечает код как "хрупкий".

## 3. DOM как API

Гарантировать стабильные CSS-классы и ID для ключевых элементов интерфейса.

**Как это работает:**
Разработчик может не иметь API для добавления кнопки в заголовок, но если он знает, что заголовок всегда имеет класс `.nh-view-header`, он может найти его через `document.querySelector` и внедрить туда свой элемент через `ReactDOM.createPortal`.

**Что нужно сделать:**
*   Добавить `data-test-id` или стабильные классы (`nh-editor-content`, `nh-sidebar-left`) везде.
*   Написать хелпер: `ctx.ui.waitForElement('.nh-sidebar-left').then(el => ...)`

## 4. Monkey Patching (Перехват функций)

Позволить плагинам подменять внутренние функции ядра.

**Пример:**
```typescript
// Плагин хочет перехватить открытие файла
const originalOpen = app.workspace.openFile;
app.workspace.openFile = async (path) => {
    console.log("Opening:", path);
    return originalOpen.call(app.workspace, path); // Вызов оригинала
}
```

**Решение для Notehub:**
Так как у нас уже есть система `api.register` / `api.invoke`, мы можем разрешить **переопределение** или **middleware** для API.

```typescript
// Плагин перехватывает сохранение
ctx.interceptApi('editor:save', async (next, ...args) => {
    console.log("Saving intercepted!");
    await backupFile();
    return next(...args);
});
```

## Итоговая рекомендация

Для максимальной гибкости "малой кровью":

1.  **Expose CodeMirror:** В `nh.features.editor` добавить команду/API `editor:get-unsafe-view`, которая возвращает объект `EditorView`. Это сразу решит проблему с insertText, выделением, скроллом и декорациями.
2.  **Expose React Components:** Разрешить плагинам импортировать базовые компоненты UI (`Button`, `Modal`, `Icon`) из `@notehub/ui`, чтобы их интерфейс выглядел нативно.
3.  **Middleware для API:** Разрешить перехват вызовов `invokeApi` (пункт 4). Это позволит плагинам менять поведение самого Notehub без изменения кода ядра.
