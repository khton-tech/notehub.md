Определение Проблематики "Live Preview"Реализация режима Live Preview является одной из сложнейших задач в инженерии текстовых редакторов. В отличие от WYSIWYG-редакторов (как ProseMirror или Tiptap), которые абстрагируют документ в дерево узлов (DOM-like schema), и в отличие от редакторов кода (как Monaco или старый CodeMirror 5), которые отображают "сырой" текст, Live Preview в Notehub.md требует гибридного подхода.Мы должны поддерживать "Единый Источник Истины" (Single Source of Truth) в виде текстового буфера Markdown, но визуально проецировать его как Rich Text. Это создает ряд архитектурных вызовов:Биективность состояния: Любое визуальное изменение (клик по чекбоксу) должно транслироваться в текстовую мутацию.Эфемерность декораций: Визуальное форматирование (скрытие ** или [ ]) должно быть обратимым без изменения самого документа.Производительность реконсиляции: Частота обновлений при наборе текста (60+ FPS) требует минимизации затрат на парсинг и DOM-манипуляции, особенно при использовании React.12. Система Инкрементального Парсинга LezerКлючевым отличием CM6 от конкурентов является использование парсера Lezer. В то время как многие Markdown-редакторы используют регулярные выражения (RegEx) для подсветки синтаксиса, что приводит к ошибкам на сложных вложенных структурах, Lezer строит полноценное синтаксическое дерево (CST - Concrete Syntax Tree).Парсер lezer-markdown обладает критически важным свойством — инкрементальностью. При изменении одного символа он перестраивает только затронутую ветвь дерева, а не весь документ. Для Notehub.md это означает, что мы можем использовать синтаксическое дерево как основу для логики скрытия разметки в реальном времени, не опасаясь лагов на больших документах.53. Архитектура Ядра Live Preview: Движок Скрытия РазметкиСердцем редактора Notehub.md станет подсистема, которую мы назовем Collapse Engine. Её задача — динамически скрывать управляющие символы Markdown (например, **, _, ``, #), когда они не нужны пользователю, и раскрывать их при редактировании.3.1. Стратегия ДекорированияДля реализации гибридного режима мы будем использовать три типа декораций, предоставляемых CM6 6:Mark Decorations: Добавляют CSS-классы или атрибуты к тексту, не меняя его структуру. Используются для стилизации (жирный, курсив, цвет ссылок).Replace Decorations: Заменяют диапазон текста на DOM-виджет (Widget) или скрывают его (если виджет пустой). Это основной инструмент для скрытия синтаксиса.Line Decorations: Применяются к контейнеру строки. Используются для стилизации заголовков (<h1>), списков и цитат.3.2. Алгоритм Пересечения Выборки (Selection Intersection)Главный вызов Live Preview — определить момент, когда разметку нужно показать. Простого CSS :hover недостаточно, так как управление должно зависеть от каретки (курсора) клавиатуры.Мы реализуем кастомный ViewPlugin, который будет работать по следующему алгоритму при каждом обновлении EditorView (Transaction) 9:Триггеры обновления: Изменение документа (docChanged), изменение выборки (selectionSet), или прокрутка (viewportChanged).Определение области видимости: Мы итерируем синтаксическое дерево только в пределах view.visibleRanges. Это критическая оптимизация производительности (O(1) относительно размера документа).1Итерация узлов:Проходим по узлам дерева Lezer (например, StrongEmphasis, Link, Header).Проверка коллизии (Intersection Check):Для каждого узла проверяем, пересекается ли текущая выборка пользователя (state.selection.main) с диапазоном узла.Если Курсор Внутри (или касается границ):Возвращаем только Mark Decoration (стиль). Разметка (**) остается видимым текстом.Если Курсор Снаружи:Вычисляем диапазоны управляющих символов (например, первые 2 и последние 2 символа для **).Применяем Replace Decoration (пустой виджет) к управляющим символам.Применяем Mark Decoration к содержимому.3.3. Техническая Реализация Плагина livePreviewPluginНиже представлен псевдокод архитектуры плагина, который должен войти в кодовую базу @notehub/editor. Этот код демонстрирует использование lezer-markdown для точного определения границ.5TypeScriptimport { ViewPlugin, Decoration, DecorationSet, EditorView, ViewUpdate } from "@codemirror/view";
import { syntaxTree } from "@codemirror/language";
import { Range } from "@codemirror/state";

// Определяем статические декорации для производительности
const hideDeco = Decoration.replace({}); // Скрывает текст
const boldStyle = Decoration.mark({ class: "cm-bold font-bold" });

export const livePreviewPlugin = ViewPlugin.fromClass(class {
  decorations: DecorationSet;

  constructor(view: EditorView) {
    this.decorations = this.compute(view);
  }

  update(update: ViewUpdate) {
    // Пересчитываем только если изменился док, выборка или вьюпорт
    if (update.docChanged |

| update.selectionSet |
| update.viewportChanged) {
      this.decorations = this.compute(update.view);
    }
  }

  compute(view: EditorView): DecorationSet {
    const widgets: Range<Decoration> =;
    const { state } = view;
    const selection = state.selection.main;

    for (const { from, to } of view.visibleRanges) {
      syntaxTree(state).iterate({
        from, to,
        enter: (node) => {
          if (node.name === "StrongEmphasis") {
            // Диапазон всего узла: **text**
            const isCursorOverlapping = 
              selection.from >= node.from && selection.to <= node.to;

            if (isCursorOverlapping) {
              // Режим редактирования: просто подсвечиваем
              widgets.push(boldStyle.range(node.from, node.to));
            } else {
              // Режим превью: скрываем маркеры
              // ВАЖНО: Хардкод длины маркера (2) опасен, в проде нужно
              // брать текст и проверять, это ** или __
              widgets.push(hideDeco.range(node.from, node.from + 2));
              widgets.push(boldStyle.range(node.from + 2, node.to - 2));
              widgets.push(hideDeco.range(node.to - 2, node.to));
            }
          }
          //... обработка других типов узлов (Link, Image, etc.)
        }
      });
    }
    return Decoration.set(widgets.sort((a, b) => a.from - b.from));
  }
}, {
  decorations: v => v.decorations,
  // ВАЖНО: Интеграция с Atomic Ranges (см. раздел 8)
  provide: plugin => EditorView.atomicRanges.of(view => {
    return view.plugin(plugin)?.decorations |

| Decoration.none;
  })
});

Решение: Atomic RangesCM6 предоставляет механизм atomicRanges, который заставляет движок выбора (Selection Engine) пропускать определенные диапазоны при навигации курсором.Мы должны интегрировать наши диапазоны скрытия в этот механизм.В конфигурации нашего livePreviewPlugin мы добавляем:TypeScriptprovide: (plugin) => EditorView.atomicRanges.of(view => {
  const pluginState = view.plugin(plugin);
  return pluginState? pluginState.decorations : Decoration.none;
})
Теперь, когда пользователь попытается войти в скрытый диапазон **, CM6 автоматически "перепрыгнет" его, поместив курсор сразу после разметки. Это обеспечивает ощущение нативности.57.2. Взаимодействие с fs-manager (IO)Поскольку мы используем Tauri, сохранение файлов происходит асинхронно. Нам нужна стратегия сохранения, устойчивая к гонкам данных.Debouncing: Мы не должны сохранять файл на каждый docChanged (каждый символ). Это создаст избыточную нагрузку на FS.Мы используем ViewUpdate слушатель с дебаунсом (например, 1000 мс).22Dirty State: Мгновенно при вводе символа мы помечаем файл как "Dirty" (грязный) в UI. После успешного сохранения сбрасываем флаг.Внешние Изменения: Если файл изменен другой программой, Tauri пошлет событие. Редактор должен обработать это. Замена всего документа (view.dispatch({ changes: { form: 0, to: doc.length, insert: newText } })) приведет к потере скролла и истории.Решение: Использовать вычисление diff (через ChangeSet) при перезагрузке файла, чтобы применить только реальные изменения, сохранив состояние редактора, если это возможно.9. Стратегия Производительности и Оптимизации9.1. Виртуализация ВьюпортаCM6 по умолчанию использует виртуализацию, рендеря только видимые строки. Наша реализация Live Preview должна строго следовать этому правилу.Правило: Никогда не запускать syntaxTree(state).iterate по всему документу в update().Исключение: Поиск ссылок для построения Backlinks (обратных ссылок). Это должно делаться в Web Worker или отдельном потоке, не блокируя UI редактора.9.2. Оптимизация React ВиджетовДаже с использованием порталов, рендеринг 1000 чекбоксов может быть тяжелым.Memoization: Компоненты виджетов должны быть обернуты в React.memo.Batching: Обновления стора виджетов должны батчиться, чтобы не вызывать 50 перерисовок React при вставке 50 параграфов текста.10. Подводные Камни и Управление Рисками10.1. IME (Input Method Editor) и КомпозицияВвод иероглифов (китайский, японский) или диакритических знаков происходит через "Композицию" (Composition). В этот момент браузер держит "виртуальный" текст, который еще не попал в DOM окончательно.Критический Баг: Если наш livePreviewPlugin попытается изменить декорации (например, скрыть разметку) во время композиции, это может "сорвать" ввод, дублировать символы или закрыть окно IME.24Решение:В методе update плагина необходимо проверять флаг view.composing.TypeScriptupdate(update: ViewUpdate) {
  if (update.view.composing) return; // Блокируем обновление декораций во время IME
  //... стандартная логика
}
Это заморозит визуальное состояние на время ввода иероглифа, что является приемлемым компромиссом ради стабильности.10.2. Доступность (A11y)Скрытие синтаксиса может запутать скринридеры. Скрытые элементы (decoration: replace) исчезают из Accessibility Tree.Рекомендация: Виджеты должны иметь атрибуты aria-hidden="true", если они чисто декоративные. Интерактивные виджеты (чекбоксы) должны иметь правильные роли и лейблы. CM6 предоставляет базовую доступность, но кастомные виджеты требуют внимания.2611. ЗаключениеПредложенная архитектура обеспечивает баланс между функциональной мощностью CodeMirror 6 и реактивной природой современного стека Notehub.md. Ключевые архитектурные столпы — это инкрементальный парсинг Lezer для управления видимостью, Atomic Ranges для корректной навигации и React Portals для интеграции UI.Реализация данной спецификации позволит создать редактор, который ощущается как нативное приложение (подобно Obsidian), сохраняя при этом полную совместимость со стандартным Markdown и расширяемость React-экосистемы. Следующим шагом является создание прототипа (Proof of Concept), реализующего базовый livePreviewPlugin и Portal Bridge.
