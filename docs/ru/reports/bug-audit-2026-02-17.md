## 1. Synapse Engine — критические проблемы

### 1.1 CRITICAL: Race condition при hot-reload плагинов

**Файл:** `packages/plugins/system/synapse/src/index.tsx:206-216`

```typescript
if (affectedPluginId) {
    await this.loader!.unloadPlugin(affectedPluginId);
    if (sourcePath) {
        await new Promise(resolve => setTimeout(resolve, 100)); // <-- ПРОИЗВОЛЬНАЯ ЗАДЕРЖКА
        await this.loadPluginByPath(sourcePath);
    }
}
```

**Проблема:** Задержка 100мс — произвольна и недетерминирована. Это классический баг TOCTOU (Time-of-Check-Time-of-Use): если файловая система ещё не завершила запись файла на диск, плагин загрузит некорректный или неполный код. На медленных дисках или при записи больших файлов 100мс недостаточно.

**Последствие:** Плагины могут не перезагрузиться или загрузить повреждённый код.

**Рекомендация:** Использовать механизм проверки стабильности файла (debounce на основе отсутствия изменений) или retry-логику с экспоненциальной задержкой.

### 1.2 CRITICAL: Отсутствие защиты от одновременного load/unload одного плагина

**Файл:** `packages/plugins/system/synapse/src/logic/PluginLoader.ts:154-261, 266-327`

```typescript
async loadPlugin(pluginPath: string): Promise<PluginLoadResult> {
    // ...
    if (this.loadedPlugins.has(manifest.id)) {   // <-- Проверка
        return { success: true, pluginId: manifest.id };
    }
    // ... Длительная загрузка ...
    this.loadedPlugins.set(manifest.id, { ... }); // <-- Установка
}
```

**Проблема:** Между проверкой `has()` (строка 187) и установкой `set()` (строка 228) проходит асинхронное время. Если два вызова `loadPlugin()` для одного ID происходят одновременно (например, hot-reload + ручная загрузка), оба пройдут проверку и загрузят плагин дважды. Аналогично, если `unloadPlugin()` вызывается во время `loadPlugin()`, состояние станет некорректным.

**Последствие:** Двойная регистрация API-методов, утечки памяти, непредсказуемое поведение.

**Рекомендация:** Ввести мьютекс (mutex) или Map с промисами-блокировками для каждого pluginId.

### 1.3 CRITICAL: cleanup() не ожидает завершения асинхронных операций

**Файл:** `packages/plugins/system/synapse/src/logic/PluginContextImpl.ts:300-380`

```typescript
cleanup(): void {  // <-- Синхронный метод!
    // ...
    for (const widgetId of this.registeredWidgets) {
        this.app.api.invoke('editor:unregister-portal', widgetId).catch(err => { ... });
        // ^^^ Promise не awaited!
    }
    for (const key of this.registeredSettingsItems) {
        this.app.api.invoke('settings:unregister-item', key).catch(() => { });
        // ^^^ Promise не awaited!
    }
    // Аналогично для groups и tabs
    this.disposed = true; // <-- Устанавливается ДО завершения unregister-вызовов
}
```

**Проблема:** Метод `cleanup()` — синхронный, но вызывает асинхронные операции (`invoke`) без ожидания их завершения. Вызывающий код (`unloadPlugin`) считает, что cleanup завершён, и удаляет плагин из реестра. Но асинхронные операции ещё выполняются, и `disposed = true` может вызвать ошибки, если invoke-вызовы ещё обращаются к контексту.

**Последствие:** Неполная очистка ресурсов. Виджеты, вкладки настроек и группы могут остаться «зомби»-записями.

**Рекомендация:** Сделать `cleanup()` асинхронным, собрать все промисы в `Promise.allSettled()`.

### 1.4 HIGH: ZipLoader — наивная перезапись bare specifiers может повредить код

**Файл:** `packages/plugins/system/synapse/src/logic/ZipLoader.ts:132-153`

```typescript
private rewriteSpecifiers(js: string): string {
    for (const [bare, url] of map) {
        js = js.replaceAll(`"${bare}"`, `"${url}"`);
        js = js.replaceAll(`'${bare}'`, `'${url}'`);
    }
    return js;
}
```

**Проблема:** Простой `replaceAll` заменяет ВСЕ вхождения строк, включая:
- Внутри комментариев: `// import 'react'`
- Внутри строковых литералов: `const msg = "I love react";`
- Внутри URL: `https://cdn.example.com/react.min.js`

**Последствие:** Код плагина может быть повреждён, если содержит строки-совпадения в неожиданных местах.

**Рекомендация:** Использовать regex с привязкой к контексту import/export-выражений, или заменять только в `from "..."` / `from '...'` конструкциях.

### 1.5 HIGH: Race condition в discoveredPlugins при scan + loadPlugin

**Файл:** `packages/plugins/system/synapse/src/logic/PluginLoader.ts:54-55, 240-252`

```typescript
async scan(vaultPath: string): Promise<void> {
    this.discoveredPlugins.clear();  // <-- Полная очистка!
    // ...
}
```

**Проблема:** Если `scan()` вызывается в момент, когда `loadPlugin()` уже загрузил плагин и обновляет `discoveredPlugins`, вызов `clear()` уничтожит эти данные. `loadPlugin` попытается обновить несуществующую запись.

**Последствие:** Несогласованное состояние: плагин загружен в `loadedPlugins`, но отсутствует в `discoveredPlugins`. UI менеджера плагинов покажет неверные данные.

### 1.6 HIGH: Не ожидаемые промисы в onPluginReady

**Файл:** `packages/plugins/system/synapse/src/index.tsx:93-104`

```typescript
this.app.api.invoke('settings:register-tab', { ... });     // <-- Promise не awaited
this.app.api.invoke('settings:register-custom-view', { ... }); // <-- Promise не awaited
```

**Проблема:** Два вызова `invoke()` возвращают промисы, которые не ожидаются. Если регистрация таба/вида упадёт, ошибка будет потеряна, и UI настроек не покажет вкладку «Plugins».

### 1.7 HIGH: Unsafe non-null assertions на loader

**Файл:** `packages/plugins/system/synapse/src/index.tsx:114-115, 196, 201, 209, 211`

```typescript
await this.loader!.scan(vaultPath);     // строка 114
await this.loader!.loadAll();            // строка 115
this.loader!.getPluginIdByPath(...)      // строка 196
await this.loader!.unloadPlugin(...)     // строка 201, 211
```

**Проблема:** Оператор `!` подавляет TypeScript-проверку на `null`. Если `onLoad()` упал до создания `loader`, или если `onUnload()` обнулил его (строка 133) во время асинхронной операции, произойдёт runtime-ошибка `Cannot read properties of null`.

**Рекомендация:** Заменить `!` на явную проверку с ранним return и логированием.

### 1.8 MEDIUM: Утечка таймера в withTimeout

**Файл:** `packages/plugins/system/synapse/src/logic/ManifestParser.ts:95-106`

```typescript
export function withTimeout<T>(promise: Promise<T>, timeoutMs: number, errorMessage: string): Promise<T> {
    return Promise.race([
        promise,
        new Promise<T>((_, reject) =>
            setTimeout(() => reject(new Error(errorMessage)), timeoutMs)
        )
    ]);
}
```

**Проблема:** Если `promise` резолвится быстро, таймер `setTimeout` продолжает работать до истечения `timeoutMs` (30 секунд). Таймер не очищается через `clearTimeout()`, что создаёт утечку ресурсов.

**Рекомендация:** Использовать `AbortController` или ручной `clearTimeout` при завершении основного промиса.

### 1.9 MEDIUM: Нет валидации содержимого массива dependencies

**Файл:** `packages/plugins/system/synapse/src/logic/ManifestParser.ts:58-60`

```typescript
if (Array.isArray(obj.dependencies)) {
    result.dependencies = obj.dependencies;  // Нет проверки элементов
```

**Проблема:** Массив `dependencies` проверяется только на тип Array. Элементы не валидируются: могут быть числами, объектами, null. Также нет проверки на циклические зависимости — Synapse вообще не детектирует циклы в зависимостях внешних плагинов (в отличие от Bootloader).

### 1.10 MEDIUM: Нет валидации формата ID манифеста

**Файл:** `packages/plugins/system/synapse/src/logic/ManifestParser.ts:35-38`

ID плагина принимается как любая строка. Нет проверки на:

### 1.11 MEDIUM: Состояние не обновляется на 'Error' при прямом вызове loadPlugin

**Файл:** `packages/plugins/system/synapse/src/logic/PluginLoader.ts:256-260`

При загрузке через `loadAll()` (строка 142), статус выставляется в `'Error'`. Но при прямом вызове `loadPlugin()` (строка 256-260) запись в `discoveredPlugins` НЕ обновляется на `'Error'` — ошибка просто возвращается в результате. UI менеджера плагинов покажет плагин как `'Inactive'` вместо `'Error'`.

### 1.12 MEDIUM: Debounce-таймер может потерять события

**Файл:** `packages/plugins/system/synapse/src/index.tsx:171-179`

`processPendingEvents()` — асинхронный, но вызывается из `setTimeout` без awaiting. Если `processPendingEvents()` занимает больше 500мс, а за это время приходят новые события, они записываются в `pendingEvents`, но `debounceTimer` уже `null` (строка 186). Новый setTimeout установится, но события из текущей обработки могут быть потеряны, если `clear()` вызовется до нового `set()`.

## 2. Bootloader и DependencyGraph

### 2.1 MEDIUM: cascadeFailure() использует рекурсию без ограничения глубины

**Файл:** `packages/plugins/system/bootloader/src/Bootloader.ts:333-345`

Рекурсивный метод `cascadeFailure()` может вызвать stack overflow при очень глубоких цепочках зависимостей (1000+ уровней). На практике маловероятно, но потенциально опасно.

**Рекомендация:** Заменить рекурсию на итеративный обход (BFS/DFS с очередью).

---

### 2.2 MEDIUM: «Зомби»-ноды в графе после buildEdges()

**Файл:** `packages/plugins/system/bootloader/src/graph/DependencyGraph.ts:113-170`

Плагины с отсутствующими зависимостями добавляются в `excludedPlugins` (локальная переменная), но **не удаляются из `this.nodes`**. Это корректно работает благодаря тому, что Bootloader помечает их failed до сортировки, но создаёт путаницу для maintainers.

---

### 2.3 MEDIUM: Нет валидации переходов состояний

**Файл:** `packages/plugins/system/bootloader/src/graph/DependencyGraph.ts:244-262`

Метод `setStatus()` не проверяет корректность переходов (PENDING → LOADED — ok, LOADED → FAILED — нежелательно). Нет state machine, некорректный переход не будет обнаружен.

---

### 2.4 LOW: Консольные предупреждения вместо структурированных ошибок

**Файл:** `packages/plugins/system/bootloader/src/graph/DependencyGraph.ts:137, 154-156`

Самозависимости и отсутствующие опциональные зависимости логируются через `console.warn()`, а не возвращаются в структурированном виде. Это несогласовано с обработкой обязательных зависимостей (которые возвращаются в массиве ошибок).

---

### 2.5 LOW: Неточная детекция участников цикла

**Файл:** `packages/plugins/system/bootloader/src/graph/TopologicalSorter.ts:140-148`

`findCycleNodes()` возвращает ВСЕ ноды с остаточным in-degree > 0, включая ноды, которые зависят от цикла, но не являются его частью. Сообщение об ошибке показывает лишние плагины.

## 3. Бекенд: FsManager, API, Core

### 3.1 HIGH: Race condition в write locks

**Файл:** `packages/plugins/system/fs-manager/src/index.ts:83-108`

```typescript
const existingLock = this.writeLocks.get(path);
const newLock = (async () => {
    if (existingLock) {
        await Promise.race([
            existingLock.catch(() => {}),
            new Promise<void>(resolve => setTimeout(resolve, WRITE_LOCK_TIMEOUT))
        ]);
    }
    await this.ensureDriver().writeFile(path, data);
})();
this.writeLocks.set(path, newLock);
```

**Проблема:** Если 3 записи (A, B, C) происходят быстро:
1. A создаёт lockA, устанавливает в Map
2. B читает lockA, создаёт lockB, устанавливает в Map
3. C читает lockB (корректно), НО если C прочитает Map до `set` B, она получит lockA

Lock не формирует надёжную цепочку. Также `Promise.race` с таймаутом означает, что при зависании предыдущей записи, новая запись начнётся параллельно, потенциально вызывая гонку данных.

**Рекомендация:** Использовать promise-chaining: `newLock = existingLock.then(() => write())`.

---

### 3.2 HIGH: Отсутствие валидации путей (Path Traversal)

**Файлы:** `packages/plugins/system/fs-manager/src/index.ts:75-80`, `packages/plugins/system/synapse/src/logic/PluginLoader.ts:56, 81`

Пути передаются напрямую в драйвер без какой-либо валидации:

```typescript
private async readTextFile(path: string): Promise<string> {
    return this.ensureDriver().readTextFile(path);  // Путь не проверяется
}
```

```typescript
const pluginsDir = `${vaultPath}/.notehub/plugins`;
const nhpPath = `${pluginsDir}/${entry.name}`;  // entry.name может содержать ../
```

**Последствие:** Вредоносный плагин или манифест с `main: "../../etc/passwd"` может выйти за пределы vault-директории.

**Рекомендация:** Нормализовать пути через `path.resolve()` и проверять, что результат находится внутри разрешённой директории.

```tsx
position: 'fixed', bottom: '20px', right: '20px'
```

На iPhone с notch, 20px справа может попасть под системные элементы. Нужен `env(safe-area-inset-right)`.

**Примечание:** В `EditorLayout.tsx:91` safe area для `paddingBottom` учтена корректно — нужно распространить паттерн на все fixed-позиционированные элементы.

### 5.5 HIGH: Кнопки слишком мелкие для touch

**Файл:** `packages/plugins/ui/ck-standard/src/components/Button.tsx:29-34`

- `sm: 'px-3 py-1.5'` — ~28px высота
- `md: 'px-4 py-2'` — ~36px высота

Стандарт iOS/Android и WCAG: минимум 44x44px для touch targets.

### 5.6 MEDIUM: TabBar не адаптирован для мобильных

**Файл:** `packages/plugins/features/tabbar/src/styles/tabbar.css:38`

`max-width: 200px` на вкладку. На узких экранах вызывает горизонтальный скролл. Нет media queries для мобильных размеров.

### 5.7 MEDIUM: Mobile drawer не имеет accessibility

**Файл:** `packages/plugins/ui/layout-manager/src/components/EditorLayout.tsx:206-230`

Drawer не имеет:
- `role="navigation"` / `aria-label`
- Ловушки фокуса (focus trap)
- Клавиатурного закрытия (Escape)

### 5.8 MEDIUM: Settings layout не адаптивен

**Файл:** `packages/plugins/ui/settings-manager/src/components/SettingsLayout.tsx:107`

```tsx
gridTemplateColumns: '280px 1fr'
```

Хардкод 280px sidebar. На планшете 768px остаётся 488px — тесно. На телефоне — вообще не помещается.

### 5.9 LOW: transition-all на мобильных снижает производительность

Множественные компоненты (EditorLayout, TabBar, Button) используют `transition-all`, который анимирует ВСЕ свойства. На мобильных устройствах это создаёт jank. Нужно указывать конкретные свойства: `transition-colors`, `transition-transform`.
