RFC-008: Стратегия мобильной архитектуры и адаптации платформы NoteHubАннотацияДанный документ представляет собой фундаментальное архитектурное исследование и техническую спецификацию (Request for Comments), разработанную для миграции платформы notehub.md на мобильную операционную систему Android с использованием среды выполнения Capacitor. В центре внимания находится адаптация сложной микроядерной архитектуры, основанной на динамической загрузке плагинов через SystemJS и использовании редактора CodeMirror 6, к строгим ограничениям мобильной среды. Документ анализирует вызовы, связанные с безопасностью WebView (CORS, доступ к файлам), предлагает алгоритмические решения для автоматической трансформации пользовательского интерфейса (Layout Adaptation), детально рассматривает низкоуровневые проблемы взаимодействия с текстом на сенсорных экранах и определяет стратегии оптимизации графической производительности. Цель спецификации — обеспечить запуск десктопной экосистемы плагинов на мобильных устройствах с минимальными изменениями в кодовой базе расширений, сохраняя при этом высокую производительность и нативный пользовательский опыт.1. Введение и Архитектурный Контекст1.1. Эволюция платформы и постановка задачиСовременная разработка программного обеспечения движется от монолитных решений к распределенным модульным системам. Платформа notehub.md представляет собой классический пример "толстого клиента" нового поколения, построенного на веб-технологиях, но использующего архитектурные паттерны операционных систем. В основе лежит микроядро (@notehub/core), которое не содержит бизнес-логики, а лишь оркестрирует жизненный цикл модулей, предоставляет шину событий и доступ к системным API.Бизнес-ценность платформы заключается в ее расширяемости. Плагины, написанные сторонними разработчиками, формируют функциональность: от рендеринга Markdown и управления задачами до интеграции с внешними облачными хранилищами. На десктопной версии (Electron/Web) эта архитектура опирается на гибкость файловой системы Node.js и отсутствие жестких ограничений безопасности браузера при работе с локальными файлами.Однако перенос этой экосистемы на мобильные устройства (Android) через Capacitor ставит перед нами ряд фундаментальных проблем. Мы не можем просто "обернуть" веб-сайт в WebView. Мы должны эмулировать среду выполнения, которая позволит коду, написанному для десктопа (полагающемуся на require, fs, мышь и клавиатуру), работать в изолированной песочнице мобильной ОС, где файловая система закрыта, сеть ограничена политиками CORS, а ввод осуществляется пальцем по виртуальной клавиатуре. Задача состоит не в переписывании плагинов, а в создании "адаптера среды" — промежуточного слоя, который транслирует намерения плагина в возможности мобильной платформы.1.2. Декомпозиция архитектуры NoteHub в контексте AndroidДля успешной миграции необходимо разобрать каждый слой приложения и определить точки отказа в мобильной среде.1.2.1. Микроядро (@notehub/core)Ядро управляет зависимостями и инициализацией. На Android оно должно взять на себя роль моста между JavaScript-кодом и нативными плагинами Capacitor. Если на десктопе ядро обращается к electron.ipcRenderer, то на мобильном устройстве оно должно использовать Capacitor.Plugins. Основной риск здесь — синхронность. Многие Node.js API синхронны, тогда как Capacitor Bridge асинхронен по своей природе (Promise-based). Это потребует внедрения слоя совместимости или изменения контрактов ядра.1.2.2. Движок плагинов (nh.system.synapse)Этот компонент использует SystemJS — универсальный загрузчик модулей. На десктопе он загружает файлы напрямую с диска через протокол file:// или через сетевые запросы. На Android WebView блокирует доступ к локальным файлам из соображений безопасности (политика Same-Origin). Это является критическим блокирующим фактором, требующим разработки собственного протокола загрузки.1.2.3. Shared Scope (Изоляция и Инъекция)Мы инжектим React, ReactDOM и API ядра в глобальную область видимости плагинов. На мобильных устройствах управление памятью становится критичным. Множество загруженных модулей могут вызвать Out-Of-Memory (OOM) killer операционной системы Android, если мы не будем контролировать потребление ресурсов и выгружать неиспользуемые плагины, что на десктопе делается редко.1.2.4. Редактор (CodeMirror 6)CodeMirror 6 — это сложный механизм, который виртуализирует рендеринг текста. Он перехватывает ввод, управляет DOM и рисует декорации. На мобильных устройствах взаимодействие с Input Method Editor (IME) — программной клавиатурой (Gboard, Samsung Keyboard) — работает иначе, чем с физической клавиатурой. События keydown могут не приходить, вместо них приходят события композиции (composition events). Это требует глубокой адаптации слоя взаимодействия редактора.2. The Runtime Challenge: Стратегия загрузки модулей SystemJS2.1. Проблематика WebView Security PolicyИсторически WebView на Android позволял загружать файлы через file://. Однако, начиная с Android API 30 и обновлений WebView v117+, Google значительно ужесточил политики безопасности.1Основная проблема заключается в Cross-Origin Resource Sharing (CORS). Если основное приложение загружается с https://localhost (что делает Capacitor по умолчанию для поддержки SPA-роутинга), то попытка загрузить скрипт плагина по адресу file:///storage/emulated/0/NoteHub/plugins/index.js будет заблокирована браузером. Протоколы https: и file: являются разными "источниками" (origins). Браузер считает это угрозой безопасности, предполагая, что веб-сайт пытается украсть локальные данные пользователя.Более того, использование file:// для основного приложения также не рекомендуется, так как это ломает механизмы History API и маршрутизации в SPA-фреймворках (React Router), а также отключает многие современные Web API, требующие безопасного контекста (Secure Context).22.2. Анализ альтернативных решенийПеред выбором целевой архитектуры мы рассмотрели три возможных подхода к решению проблемы загрузки модулей.2.2.1. Подход A: Локальный HTTP-серверИдея заключается в запуске нативного веб-сервера (например, NanoHTTPD на Java) внутри Android-приложения, который раздает файлы плагинов на http://localhost:8080.Плюсы: Полная совместимость с браузерными fetch и <script src="...">. CORS решается настройкой заголовков сервера.Минусы: Высокое потребление батареи, сложности с управлением жизненным циклом (сервер нужно глушить в фоне), потенциальные конфликты портов. Самое главное — риски отказа в публикации в Google Play и App Store, так как локальные веб-серверы часто используются для обхода модерации кода.3Вердикт: Отклонено.2.2.2. Подход B: Перехват запросов через CapacitorHttpИспользование плагина CapacitorHttp, который патчит глобальные window.fetch и XMLHttpRequest, перенаправляя их через нативный слой.4Плюсы: Позволяет обходить CORS для сетевых запросов.Минусы: Этот плагин предназначен в первую очередь для HTTP-запросов к внешним API. Он не предназначен для эффективного чтения локальных файлов. Оверхед на сериализацию данных через мост Capacitor для каждого JS-файла может быть значительным.Вердикт: Возможно для API, но не оптимально для загрузки кода.2.2.3. Подход C: Custom Protocol + Filesystem Interception (Целевое решение)Мы создаем виртуальный протокол (например, plugin:// или перехватываем запросы SystemJS) и используем прямой доступ к файловой системе через Capacitor Filesystem API. Это решение не требует поднятия сервера и работает полностью внутри процесса приложения.2.3. Техническая спецификация Plugin Loading ProtocolМы выбираем стратегию переопределения хука загрузки SystemJS (Fetch Hook Override). SystemJS 6+ предоставляет мощный API для кастомизации процесса получения исходного кода модулей. Вместо того чтобы полагаться на браузерный fetch, мы внедрим функцию, которая обращается к нативному слою Android.2.3.1. Архитектура Native LoaderПроцесс загрузки плагина будет выглядеть следующим образом:Запрос: Ядро инициирует загрузку модуля System.import('plugin://my-plugin/index.js').Перехват (Interception): Кастомный fetch хук в SystemJS обнаруживает префикс plugin://.Мост (Bridge Call): JS-слой вызывает Filesystem.readFile() из @capacitor/filesystem.Нативное чтение (Native Read): Java-код считывает файл из Directory.Documents или Directory.ExternalStorage (в зависимости от прав доступа и версии Android).Возврат данных: Содержимое файла возвращается в виде строки (UTF-8). Важно избегать возврата Base64 для текстовых файлов, чтобы не тратить процессорное время на декодирование в JS.6Эмуляция ответа: Мы конструируем объект Response (Web API), содержащий текст скрипта, и возвращаем его в SystemJS.Исполнение: SystemJS транспилирует (если нужно) и исполняет код в глобальном контексте.2.3.2. Детальная реализация хука (TypeScript)Ниже представлен код, который должен быть выполнен на этапе инициализации приложения (bootstrapping), до загрузки любых плагинов.TypeScriptimport { Filesystem, Directory, Encoding } from '@capacitor/filesystem';
import { Capacitor } from '@capacitor/core';

// Интерфейс для конфигурации хука
interface NativeLoaderConfig {
  basePluginPath: string; // Базовый путь к папке плагинов на устройстве
}

export const registerSystemJSNativeLoader = (config: NativeLoaderConfig) => {
  const originalFetch = window.fetch;

  // Переопределение fetch в SystemJS
  // @ts-ignore - Расширение прототипа SystemJS
  System.constructor.prototype.fetch = async function (url: string, options?: any) {
    
    // 1. Проверка протокола
    if (url.startsWith('plugin://') |

| url.startsWith('file://')) {
      // Логирование для отладки
      console.debug(` Native load intercepted: ${url}`);

      try {
        // 2. Нормализация пути
        // Удаляем протокол, чтобы получить чистый путь для Filesystem API
        // На Android пути могут быть сложными: /storage/emulated/0/...
        let path = url.replace(/^(plugin|file):\/\//, '');
        
        // Обработка относительных путей, если они возникли
        if (path.startsWith('/_capacitor_file_/')) {
            path = path.replace('/_capacitor_file_/', '');
        }

        // 3. Вызов Native Filesystem API
        // Использование Encoding.UTF8 критично для получения строки, а не blob/base64
        const result = await Filesystem.readFile({
          path: path,
          // Внимание: для абсолютных путей directory часто не указывается,
          // либо используется Directory.ExternalStorage как корень.
          // Это зависит от того, где физически лежат плагины.
          encoding: Encoding.UTF8
        });

        // 4. Валидация данных
        if (typeof result.data!== 'string') {
           throw new Error('Plugin file content is not a string');
        }

        // 5. Конструирование ответа
        // SystemJS ожидает fetch-like Response
        return new Response(result.data, {
          status: 200,
          statusText: 'OK',
          headers: { 
            'Content-Type': 'application/javascript',
            'X-Source': 'Capacitor-Filesystem'
          }
        });

      } catch (error) {
        console.error(` Failed to load native module: ${url}`, error);
        
        // Возвращаем корректную ошибку 404, чтобы SystemJS мог обработать её
        return new Response(null, { 
            status: 404, 
            statusText: `Not Found: ${error.message}` 
        });
      }
    }

    // Фоллбэк на стандартный fetch для http/https зависимостей (например, CDN)
    return originalFetch(url, options);
  };
  
  // Дополнительный хук 'resolve' может понадобиться для маппинга "голых" импортов
  const originalResolve = System.constructor.prototype.resolve;
  System.constructor.prototype.resolve = function (id: string, parentUrl?: string) {
      // Здесь можно реализовать логику Magic Imports
      // Например, перенаправление require('fs') на заглушку
      if (id === 'fs' |

| id === 'path') {
          return System.resolve('app://polyfills/node-mock.js');
      }
      return originalResolve.call(this, id, parentUrl);
  };
};
Анализ безопасности и ограничений:Использование Filesystem.readFile обходит CORS, так как данные передаются через мост Capacitor, который технически не является сетевым запросом. Однако, необходимо учитывать разрешения Android. Для доступа к файлам в Directory.Documents или произвольным путям на Android 11+ (API 30+) приложение должно запросить разрешение MANAGE_EXTERNAL_STORAGE (если оно является файловым менеджером) или использовать Storage Access Framework (SAF). В контексте NoteHub, плагины лучше всего хранить в приватной директории приложения (Directory.Data или Directory.Library на iOS), к которой доступ всегда разрешен без дополнительных прав.6Если плагины загружаются пользователем извне (Download), нам придется использовать MediaStore API или SAF для копирования их во внутреннее хранилище перед использованием. Прямое чтение из папки Downloads может быть нестабильным на новых версиях Android.2.4. Обеспечение работы import без сети (Offline-First)Плагины часто имеют внешние зависимости (например, import _ from 'lodash'). На десктопе они резолвятся из node_modules. Концептуальный разрыв: Desktop vs MobileДесктопный интерфейс notehub.md использует паттерн "Command Center": высокая плотность информации, постоянное присутствие панелей инструментов (Ribbon), боковых панелей (Sidebar) и строки состояния. Специфика CodeMirror 6 на AndroidРедактор кода — сердце платформы. CodeMirror 6 (CM6) спроектирован с учетом спецификации contenteditable, но мобильные браузеры (особенно Chrome на Android) имеют специфическую реализацию ввода, известную как Composition (Композиция).4.1.1. Проблема: "The Backspace Bug"На десктопе нажатие Backspace отправляет событие keydown с кодом 8. Редактор перехватывает его и удаляет символ.На Android виртуальная клавиатура (Gboard) работает иначе. Она не посылает нажатия клавиш для каждого символа. Вместо этого она мутирует содержимое DOM напрямую или посылает события compositionupdate. Когда пользователь нажимает Backspace, клавиатура может попытаться сократить слово в своем буфере и обновить DOM.Конфликт возникает, когда в тексте есть "нередактируемые" виджеты (React Portals, инжектируемые плагинами, например, математические формулы или блоки кода). Если курсор стоит после такого виджета, и пользователь нажимает Backspace, Android часто не понимает, что нужно удалить "атомарный" элемент, а не символ. Это приводит к тому, что удаление не срабатывает, или клавиатура "схлопывается" (закрывается).104.1.2. Решение: Патчинг редактора (Zero-Width Space)Для решения этой проблемы необходимо внедрить расширение CodeMirror, которое окружает атомарные виджеты символами нулевой ширины (Zero-Width Space, \u200b). Это заставляет Android IME "видеть" текст вокруг виджета и корректно обрабатывать позицию курсора и удаление.Дополнительно необходимо настроить inputMode для скрытых полей ввода, которые CodeMirror использует для захвата фокуса, чтобы клавиатура появлялась корректно.124.2. Абстракция жестов (Gesture Mapping)Десктопные плагины полагаются на hover, contextmenu (Right Click) и горячие клавиши (Ctrl+C). Нам нужен слой эмуляции.4.2.1. Контекстное меню через Long PressНа Android нет правой кнопки мыши. Событие contextmenu может сработать при долгом нажатии, но оно часто конфликтует с системным выделением текста.Реализация:Мы перехватываем событие touchstart. Если палец удерживается на элементе более 500мс без движения (порог touchmove), мы:Блокируем всплытие нативного события (e.preventDefault()).Генерируем синтетическое событие, которое система плагинов воспринимает как запрос контекстного меню.Критически важно: Запускаем тактильный отклик (Haptic Feedback). Без вибрации пользователь не поймет, что долгое нажатие сработало.Код интеграции Haptics:TypeScriptimport { Haptics, ImpactStyle } from '@capacitor/haptics';

// Функция вызова вибрации
async function triggerHapticFeedback() {
  await Haptics.impact({ style: ImpactStyle.Medium });
}

// Внутри обработчика жестов
onLongPress: () => {
  triggerHapticFeedback();
  showActionSheet(contextMenuOptions);
}
Использование ImpactStyle.Medium 14 наиболее близко имитирует "щелчок" механической кнопки или Taptic Engine на iOS.4.2.2. Управление виртуальной клавиатурой (Keyboard Insets)Одна из самых больших болей мобильного веба — клавиатура, перекрывающая поле ввода. Стандартное поведение window.resize не всегда надежно.Стратегия:Использовать Visual Viewport API: window.visualViewport.height дает реальную высоту видимой области за вычетом клавиатуры.Использовать плагин @capacitor/keyboard для получения точных событий keyboardWillShow и keyboardWillHide.При открытии клавиатуры мы динамически меняем padding-bottom у контейнера прокрутки CodeMirror, добавляя высоту клавиатуры + высоту Accessory Bar. Это позволяет пользователю прокрутить текст так, чтобы каретка (курсор) всегда была видима и не пряталась за клавиатурой.5. Performance Constraints: Оптимизация графики5.1. Проблема backdrop-filterВ дизайне NoteHub для десктопа активно используется эффект размытия фона (backdrop-filter: blur(20px)) для создания эффекта глубины (Glassmorphism) в Ribbon и боковых панелях.На мобильных GPU, особенно в архитектурах с тайловым рендерингом (Tile-based rendering, используемым в ARM Mali и Qualcomm Adreno), операция backdrop-filter является экстремально дорогой. Она требует от GPU прервать текущий проход рендеринга, прочитать уже отрисованные пиксели из буфера кадра (read-back), применить к ним свертку (blur) и записать обратно.Исследования и опыт сообщества показывают, что на Android WebView это часто приводит к падению FPS до 10-15 кадров в секунду при скролле, даже на флагманских устройствах.16 Это делает интерфейс "вязким" и неприятным.5.2. Стратегия "Degradation Gracefully" (Изящная деградация)Необходимо внедрить механизм адаптации темы на уровне CSS и JS.Решение:CSS Feature Query (недостаточно): Просто проверка @supports (backdrop-filter: blur()) вернет true на современных Android, но не скажет нам, что это будет тормозить.Platform-based CSS Class: При старте приложения мы добавляем класс platform-android к <body>.CSS Overrides:CSS/* Десктоп по умолчанию */
.glass-panel {background: rgba(255, 255, 255, 0.7);backdrop-filter: blur(20px);-webkit-backdrop-filter: blur(20px);}/* Оптимизация для Android */
body.platform-android.glass-panel {
  /* Отключаем блюр, увеличиваем непрозрачность для читаемости */
  background: rgba(255, 255, 255, 0.96);
  backdrop-filter: none;
  -webkit-backdrop-filter: none;
  
  /* Добавляем легкую тень или бордер для разделения слоев */
  box-shadow: 0 4px 6px rgba(0,0,0,0.05);
  border-bottom: 1px solid rgba(0,0,0,0.1);
}
```
Это решение кардинально улучшает производительность скролла и анимаций открытия меню, жертвуя лишь незначительным визуальным украшательством.6.
