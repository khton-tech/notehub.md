Введение и Архитектурный Контекст1.1. Эволюция архитектуры редактора: От Монолита к Портальной СистемеВ современном ландшафте разработки инструментов для создания заметок и баз знаний (Knowledge Base tools) мы наблюдаем фундаментальный сдвиг парадигмы. Традиционные WYSIWYG-редакторы, построенные на базе contentEditable с жесткой привязкой к DOM-структуре (такие как ранние версии CKEditor или Draft.js), достигают предела своей масштабируемости и расширяемости. В контексте разработки ядра notehub.md мы столкнулись с классической проблемой "архитектурного бутылочного горлышка": попытка реализовать сложные интерактивные элементы — кнопки, динамические графики, таблицы с живыми данными — внутри монолитного цикла рендеринга текстового редактора приводит к экспоненциальному росту сложности поддержки и деградации производительности.Мы отказываемся от монолитного подхода в пользу микро-фронтенд архитектуры, которую мы обозначаем как "Portal System". В этой концепции CodeMirror 6 (CM6) перестает быть "владельцем" всего визуального представления. Вместо этого он понижается в ответственности до уровня высокопроизводительного "холста" (Smart Canvas), отвечающего исключительно за управление текстовым состоянием, виртуализацию вьюпорта, обработку ввода и управление курсором. Рендеринг "богатого" контента (Rich Content) делегируется внешней, специализированной системе — React 18+, которая инжектирует компоненты через механизм React Portals.1Эта архитектура решает ключевую дилемму современных редакторов кода и текста: противоречие между строгой текстовой моделью и необходимостью отображения произвольных UI-элементов. Использование CodeMirror 6, который является полностью переписанным движком с акцентом на доступность, поддержку тачскринов и, что наиболее важно, расширяемость 1, предоставляет нам необходимый фундамент. CM6 является агностиком по отношению к фреймворкам, что позволяет интегрировать React не как "надстройку", а как равноправный слой рендеринга.11.2. Концепция "Live Preview Portals" и UX-императивыЦентральным элементом нашей новой архитектуры является концепция "Live Preview Portals". Это гибридный режим взаимодействия, который объединяет преимущества работы с исходным кодом (Markdown) и визуального редактирования (WYSIWYG). Мы используем синтаксис вида ] (например, ]) как источник правды.Пользовательский опыт (UX) определяется состоянием "Cursor Dance" (Танец Курсора):View Mode (Режим Просмотра): Когда курсор редактирования находится вне границ синтаксической конструкции, текстовое представление коллапсирует. Вместо сырого текста рендерится полноценный React-компонент (виджет). Это создает иллюзию документа с богатым форматированием.Edit Mode (Режим Редактирования): Как только курсор касается границ блока или входит в него, "магия" рассеивается. React-компонент скрывается (или становится полупрозрачным), и пользователю открывается исходный код конструкции для прямого редактирования.Эта механика накладывает строгие требования на производительность системы обнаружения пересечений (Intersection Logic) и управление жизненным циклом компонентов, чтобы избежать визуальных артефактов ("мигания", FOUC) и утечек памяти при быстром скролле или редактировании больших документов (50k+ строк).32. Dynamic Parsing Strategy: Динамическая Токенизация2.1. Ограничения статической грамматики LezerCodeMirror 6 использует Lezer — инкрементальный парсер, который строит синтаксическое дерево (Syntax Tree) на основе заранее скомпилированной грамматики. Это обеспечивает высокую производительность и устойчивость к ошибкам. Однако, архитектура notehub.md требует динамической загрузки плагинов (например, @notehub/portal-button, @notehub/portal-chart). Мы не можем знать весь набор синтаксических конструкций на этапе сборки приложения (build time).Исследование экосистемы CM6 подтверждает, что LR-парсеры, используемые в Lezer, компилируются в таблицы состояний, которые невозможно эффективно расширять в рантайме без полной перекомпиляции или использования сложных и хрупких механизмов "вклейки" грамматик, что часто приводит к нестабильности.6 Форк грамматики Markdown для каждого плагина не является жизнеспособной стратегией масштабирования.62.2. Стратегия MatchDecorator и ViewPluginДля реализации динамических "shortcodes" вида [[...]], которые семантически ближе к инлайн-токенам, чем к глубокой вложенной структуре, оптимальным решением является использование регулярных выражений в сочетании с классом MatchDecorator из пакета @codemirror/view.7MatchDecorator позволяет сканировать документ на наличие паттернов и автоматически применять декорации (Decorations) к найденным диапазонам. Ключевое преимущество этого подхода перед попыткой внедрения в AST Lezer заключается в том, что MatchDecorator работает поверх видимых диапазонов (visibleRanges), что критически важно для производительности. При работе с документами объемом 50,000 строк перестройка полного AST при каждом нажатии клавиши вызвала бы неприемлемые задержки (input latency).8Сравнительный анализ подходов к парсингуХарактеристикаКомпиляция Lezer GrammarRuntime Regex (MatchDecorator)Ручной ViewPluginДинамичностьНизкая (требует build step)Высокая (RegExp из конфига)ВысокаяПроизводительность (Small Doc)Экстремально высокаяВысокаяСредняяПроизводительность (50k Lines)Высокая (Incremental)Высокая (Viewport only) 9Зависит от реализацииСложность внедренияВысокая (Forking grammar) 6Низкая (Built-in API)ВысокаяУстойчивость к ошибкамВысокаяНизкая (Regex fragility)НизкаяРешение: Мы используем композицию ViewPlugin, который управляет экземплярами MatchDecorator. Каждый загружаемый плагин региструет свой RegExp. Ядро редактора агрегирует эти выражения. Чтобы избежать конфликтов перекрывающихся правил, мы применяем стратегию "First Match Wins" или, в более сложных случаях, объединяем регулярные выражения в единый мастер-паттерн, если это позволяет синтаксис JS RegExp.2.3. Проблема производительности больших документов (The 50k Lines Challenge)При работе с документами большого объема (50k+ строк) возникают специфические проблемы производительности, связанные с токенизацией. Как отмечено в 9 и 5, CodeMirror применяет оптимизацию, при которой очень длинные строки не рендерятся целиком, а частично скрываются. MatchDecorator по умолчанию работает только с видимыми диапазонами. Это означает, что если строка кода (например, минифицированный JSON) превышает лимит (по умолчанию 10,000 символов), сканирование может прерваться, и портал в конце строки не будет отрисован.9Для notehub.md, где пользователи могут вставлять большие блоки данных, мы должны настроить параметр maxLength в конфигурации декоратора. Установка этого значения в Infinity 10 не рекомендуется, так как это может "повесить" браузер на строке в 50k символов.5 Мы принимаем архитектурное решение ограничить длину строки, внутри которой возможен парсинг порталов, разумным пределом (например, 20,000 символов), что покрывает 99.9% реальных кейсов использования заметок, сохраняя отзывчивость интерфейса. Виртуализация вьюпорта (viewportMargin) в CM6 работает эффективно, и пока мы не заставляем парсер обрабатывать весь документ синхронно, производительность останется на уровне O(N), где N — размер видимой области, а не всего документа.43. The Portal Bridge: Архитектура React-CM6 Моста3.1. Single Root Provider PatternОдной из наиболее распространенных ошибок при интеграции React и CodeMirror является попытка рендеринга React-дерева для каждого виджета индивидуально (через ReactDOM.createRoot или render внутри метода toDOM виджета).2 Этот подход, "Multiple Roots", приводит к изоляции контекста: порталы теряют доступ к Redux Store, ThemeContext, I18nProvider и другим провайдерам, находящимся выше в дереве приложения.2Мы утверждаем архитектуру "Single Root Provider". Существует единственный компонент-оркестратор <PortalRenderer>, который находится в основном дереве React приложения notehub.md. CodeMirror через свой плагин (Bridge) лишь сообщает этому оркестратору: "Мне нужен компонент типа BUTTON в DOM-узле с ID uuid-123". Оркестратор использует ReactDOM.createPortal для "телепортации" уже отрендеренного React-компонента в указанный DOM-узел, созданный CM6.3.2. Registry и Жизненный Цикл (Lifecycle Management)Система должна поддерживать реестр активных порталов. Когда CM6 создает виджет, он вызывает метод регистрации.Проблема Reconciliation и FOUC:CodeMirror пересоздает DOM-элементы при скролле и обновлении документа гораздо агрессивнее, чем React. Существует риск "мигания" (Flash of Unstyled Content - FOUC), когда CM6 уже создал пустой <span>, а React еще не успел смонтировать туда портал асинхронно.1Для минимизации этого эффекта, виджеты CM6 (WidgetType.toDOM) должны создавать DOM-структуру с фиксированными размерами (если известны) или спиннером-скелетоном, который мгновенно заменяется контентом портала.Управление Памятью (Memory Management):Критически важным аспектом является очистка ресурсов. Когда строка с порталом удаляется или уходит из вьюпорта (виртуализация), CM6 удаляет DOM-узел. Однако React не знает об этом автоматически, что приводит к утечкам памяти ("зомби-порталы").12Метод destroy(dom) класса WidgetType в CM6 — это точка синхронизации. Мы обязаны реализовать этот метод, чтобы отправлять сигнал unregister в наш Portal Store. Как подтверждено в 13, этот метод вызывается корректно при удалении виджета из DOM, что позволяет нам безопасно размонтировать React-компонент.3.3. 4. Live Preview Interaction: "The Cursor Dance"Самая сложная часть UX — это корректная обработка взаимодействия курсора с порталами. Мы называем это "Танцем Курсора".4.1. Логика Пересечений (Intersection Logic)Для реализации поведения "View Mode -> Edit Mode" нам необходимо динамически менять тип декорации в зависимости от позиции курсора (Selection).Мы используем ViewPlugin, который на каждом обновлении (update) проверяет пересечение текущего выделения (state.selection.ranges) с диапазонами найденных порталов.Алгоритм:Плагин получает набор диапазонов порталов (парсинг через MatchDecorator).Для каждого портала проверяется условие: Selection Overlaps Range.Если пересечение есть: Мы применяем Decoration.mark. Это оставляет текст видимым, но позволяет стилизовать его (например, сделать серым), показывая, что это "сырой код" портала.Если пересечения нет: Мы применяем Decoration.replace. Это скрывает текст и вместо него вставляет WidgetType (наш портал).Этот подход требует высокой эффективности, так как проверка происходит на каждый transaction (каждое движение курсора). Использование RangeSet и итераторов CM6 позволяет выполнять эти проверки за логарифмическое время, что приемлемо даже для сотен порталов.34.2. Атомарные Диапазоны (Atomic Ranges)Когда портал находится в режиме View (скрытый текст, видимый виджет), он должен вести себя как единый символ. Пользователь не должен иметь возможности поместить курсор в середину скрытого текста ] при навигации стрелками.Для этого используется фасет EditorView.atomicRanges. Мы должны передавать в этот фасет те же диапазоны, которые в данный момент скрыты (Decoration.replace).7Проблема "Ловушки Курсора" (Cursor Trap):Исследования 16 и 17 выявляют серьезную проблему: если пользователь кликнет мышью или использует специфическую навигацию, курсор может оказаться "запертым" внутри атомарного диапазона, или поведение навигации может стать непредсказуемым.Решение заключается в использовании transactionFilter. Мы можем перехватывать транзакции, которые пытаются установить курсор внутрь активного (свернутого) портала, и корректировать позицию курсора, сдвигая его к ближайшей границе (start или end).17Однако, в нашей концепции "Cursor Dance", попадание курсора внутрь диапазона должно разворачивать его. Поэтому логика atomicRanges должна быть динамической: диапазон является атомарным только если курсор находится снаружи. Как только курсор (например, при клике) пытается войти, мы разрешаем это действие, и на следующем такте рендеринга ViewPlugin убирает Decoration.replace, превращая диапазон в обычный текст.4.3. Псевдокод ViewPlugin (Implementation Strategy)TypeScript// Концептуальная реализация логики видимости
const portalPlugin = ViewPlugin.fromClass(class {
  decorations: DecorationSet;

  constructor(view: EditorView) {
    this.decorations = this.compute(view);
  }

  update(update: ViewUpdate) {
    // Пересчитываем только если изменился документ, выделение или вьюпорт
    if (update.docChanged |

| update.selectionSet |
| update.viewportChanged) {
      this.decorations = this.compute(update.view);
    }
  }

  compute(view: EditorView): DecorationSet {
    let widgets =;
    // Используем сохраненный MatchDecorator для поиска всех тегов
    // Iteration optimization: only scan visible ranges 
    for (let {from, to, match} of parsedRanges(view)) {
      const selection = view.state.selection.main;
      // Intersection Logic
      const cursorInside = selection.from >= from && selection.to <= to; 
      // Или более широкая проверка на касание границ:
      // const touching = selection.to >= from && selection.from <= to;

      if (cursorInside) {
        // Edit Mode: Just style the text
        widgets.push(Decoration.mark({class: "cm-portal-edit"}).range(from, to));
      } else {
        // View Mode: Replace text with Widget
        widgets.push(Decoration.replace({
          widget: new PortalWidget(match),
          inclusive: false // Разрешаем курсору подходить вплотную
        }).range(from, to));
      }
    }
    return Decoration.set(widgets);
  }
}, {
  decorations: v => v.decorations,
  // Atomic ranges mapping [7, 19]
  provide: PluginField.atomicRanges.from(v => v.decorations)
});

Стилизация: Shadow DOM vs Shared ContextВопрос изоляции стилей является критическим для микро-фронтендов.Использование Shadow DOM для каждого отдельного виджета (например, для каждой кнопки в тексте) является избыточным и может негативно сказаться на производительности (тысячи Shadow Roots). Кроме того, CM6 имеет свои сложности с работой внутри Shadow DOM, связанные с внедрением глобальных стилей редактора.20Рекомендация:Мы рекомендуем использовать Shared Context и CSS Modules (или Scoped CSS) вместо Shadow DOM на уровне виджетов.Глобальные стили редактора (темы) передаются в <PortalRenderer> через React Context.Каждый плагин портала должен использовать уникальные префиксы классов или CSS-in-JS решения для предотвращения конфликтов стилей.Shadow DOM целесообразно использовать только на уровне самого редактора (<notehub-editor>), чтобы изолировать его от остальной страницы, но не внутри виджетов.20 Если редактор находится в Shadow DOM, необходимо корректно пробрасывать root (shadowRoot) в конфигурацию EditorView, чтобы CM6 мог правильно обрабатывать события и фокус.116. 6.3. Code Strategy: Реализация PortalWidget и PortalRendererРеализация WidgetType (The Bridge)TypeScriptimport { WidgetType } from "@codemirror/view";
import { portalRegistry } from "./portalRegistry"; // Singleton or Context

export class PortalWidget extends WidgetType {
  private id: string;
  
  constructor(
    readonly type: string,
    readonly payload: any,
    readonly component: React.ComponentType<any>
  ) {
    super();
    this.id = crypto.randomUUID(); // Уникальный ID для React key
  }

  // Сравнение виджетов для предотвращения лишних перерисовок DOM
  eq(other: PortalWidget) {
    return other.type === this.type && JSON.stringify(other.payload) === JSON.stringify(this.payload);
  }

  toDOM(view: EditorView) {
    const span = document.createElement("span");
    span.className = "cm-portal-widget";
    span.style.minHeight = "24px"; // Prevention of FOUC/Layout shift
    span.style.display = "inline-block";
    
    // Регистрация в сторе. React подхватит это и отрендерит портал внутрь span.
    portalRegistry.register(this.id, {
      id: this.id,
      component: this.component,
      container: span,
      props: { 
        data: this.payload, 
        view, 
        getPos: () => view.posAtDOM(span) // Dynamic position lookup 
      }
    });

    return span;
  }

  updateDOM(dom: HTMLElement, view: EditorView) {
    // Если виджет обновляется (eq вернул false, но тип тот же), обновляем пропсы
    portalRegistry.update(this.id, { 
      data: this.payload,
      view,
      getPos: () => view.posAtDOM(dom)
    });
    return true; // Возвращаем true, чтобы CM6 не пересоздавал DOM-узел
  }

  destroy(dom: HTMLElement) {
    // Критически важно: очистка памяти 
    portalRegistry.unregister(this.id);
  }
}
