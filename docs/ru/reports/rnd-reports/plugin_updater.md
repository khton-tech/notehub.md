Введение: Кризис Контроля и Смена Парадигмы1.1. Архитектурный Тупик "Песочницы"В процессе эволюции программных платформ, поддерживающих сторонние расширения, неизбежно наступает момент, который мы называем "Кризисом Контроля". Текущая архитектура Notehub.md, построенная на принципах изолированной "песочницы" (Sandbox), достигла предела своей эффективности. Мы столкнулись с классической дилеммой, описанной в теории проектирования систем: попытка обеспечить абсолютную безопасность через ограничение API приводит к экспоненциальному росту сложности "мостов" (bridges) и адаптеров, необходимых для удовлетворения все более сложных требований разработчиков.Традиционная модель, где ядро системы предоставляет жестко типизированный, ограниченный набор методов ("Safe API"), базируется на ложной предпосылке, что архитекторы ядра способны предвидеть все возможные сценарии использования их продукта. История развития таких экосистем, как Eclipse, Visual Studio Code или Obsidian, доказывает обратное: инновации чаще всего рождаются "на краю" (at the edge), в пространстве, которое изначально не предусматривалось создателями платформы.2Текущий анализ показывает, что искусственные барьеры безопасности, призванные защитить целостность приложения, парадоксально угрожают его жизнеспособности. Разработчики плагинов, сталкиваясь с невозможностью легитимно модифицировать поведение редактора (например, перехватить операцию сохранения для шифрования или изменить рендеринг DOM-элемента), прибегают к хрупким "хакам", monkey-patching глобальных объектов и инъекциям скриптов, которые невозможно контролировать или отлаживать. Это создает экосистему "теневого API", которая дестабилизирует платформу гораздо сильнее, чем открытый доступ.31.2. Философия Суверенной АрхитектурыВ ответ на эти вызовы мы предлагаем радикальную смену парадигмы, которую мы называем "Суверенная Архитектура" (The Sovereign Architecture) или, в более технической терминологии, Open Core with Trust (Открытое ядро с доверием).Суть этой концепции заключается в отказе от иллюзии полного контроля. Вместо того чтобы строить все более высокие стены вокруг ядра, мы должны предоставить инфраструктуру, которая делает любое вмешательство в работу системы:Прозрачным (Transparent): Любое действие проходит через наблюдаемые каналы.Управляемым (Manageable): Вмешательство имеет четко определенный приоритет и место в цепочке исполнения.Обратимым (Reversible): Система может изолировать сбойный компонент без краха всего приложения.В рамках RFC-010 v2 мы объединяем две мощные концепции:Unsafe Context ("God Mode"): Предоставление прямого доступа к внутренним структурам (React instance, CodeMirror View, DOM) через специфицированные "аварийные люки".The Hook System (Interceptors): Переход от императивного вызова команд к пайплайну обработки сообщений (Middleware Chain), позволяющему перехватывать, модифицировать и блокировать любые API-вызовы.4Мы постулируем, что система должна обладать способностью к "самолечению" (self-patching). Если в ядре обнаружен баг, мы не должны ждать следующего релиза монолита. Архитектура должна позволять выпустить микро-плагин ("Patcher"), который перехватывает проблемный вызов и исправляет его поведение на лету. Это требует перехода от статической архитектуры к динамической, основанной на потоках сообщений.2. Фундамент Среды Выполнения: SystemJS и JSX RuntimeПрежде чем мы сможем реализовать высокоуровневые абстракции перехвата, необходимо устранить фундаментальный дефект в слое загрузки модулей. Без надежного Runtime никакие хуки не имеют смысла, так как плагины просто не смогут загрузиться.2.1. Анатомия Проблемы Разрешения МодулейОдной из наиболее острых проблем, блокирующих вход новых разработчиков в экосистему Notehub.md, является несовместимость текущей конфигурации загрузчика SystemJS с современным стандартом трансформации JSX, внедренным в React 17+ (новый JSX Transform).52.1.1. Эволюция JSX и Конфликт с SystemJSДо версии 17 React требовал импорта React в скоупе любого файла, использующего JSX, так как транспиляторы (Babel, TypeScript) преобразовывали теги <div /> в вызовы React.createElement('div'). Современные сборщики (Vite, Webpack 5+, Rollup), используемые при создании плагинов сегодня, по умолчанию применяют режим jsx: "automatic". В этом режиме компилятор не использует React.createElement. Вместо этого он автоматически добавляет импорты из специальной точки входа: react/jsx-runtime (для продакшена) или react/jsx-dev-runtime (для разработки).6Проблема возникает на стыке стандартов модулей. В среде Node.js (CommonJS) или при использовании нативных ES-модулей с Node-style resolution, запрос react/jsx-runtime корректно разрешается в файл внутри пакета react. Однако, в браузере под управлением SystemJS отсутствует автоматическое "магическое" разрешение путей внутри NPM-пакетов. SystemJS полагается на Import Maps (Карты импортов).7Текущая карта импортов платформы (systemjs-importmap) обычно содержит запись для корневого пакета react, но не содержит явных указаний для его подмодулей. Когда браузер пытается выполнить код плагина, содержащий строку import { jsx } from 'react/jsx-runtime', SystemJS обращается к реестру, не находит точного совпадения и выбрасывает фатальное исключение:Error: Unable to resolve bare specifier 'react/jsx-runtime'.Это создает ситуацию "DLL Hell" в браузере: разработчик плагина не может использовать современные инструменты, а платформа не может загрузить современный код.2.2. Стратегия Гибридной Карты ИмпортовДля решения этой проблемы мы не можем полагаться на автоматическое поведение. Мы должны внедрить детерминированную стратегию разрешения модулей, которая сочетает в себе явную конфигурацию Import Map и "синтетическую" регистрацию модулей в памяти.2.2.1. Расширение Import Map (Уровень Index.html)Первый слой защиты — это явное декларирование необходимых путей в index.html. Мы должны сообщить SystemJS, что запрос react/jsx-runtime является валидным и должен разрешаться специфическим образом.В отличие от стандартного подхода, где каждый файл загружается по сети, мы используем стратегию Named Bundles (Именованных Бандлов). Поскольку ядро Notehub.md уже содержит React, мы не хотим загружать его заново. Мы хотим перенаправить запросы плагинов на уже загруженные инстансы внутри ядра.В index.html мы определяем маппинг на внутреннее пространство имен app::HTML<script type="systemjs-importmap">
{
  "imports": {
    "react": "app:react",
    "react-dom": "app:react-dom",
    "react/jsx-runtime": "app:react/jsx-runtime",
    "@notehub/api": "app:notehub-api",
    "@codemirror/view": "app:codemirror/view",
    "@codemirror/state": "app:codemirror/state"
  }
}
</script>
Этот маппинг говорит SystemJS: "Не пытайся загрузить файл для react/jsx-runtime. Вместо этого ищи модуль с именем app:react/jsx-runtime в своем внутреннем реестре".72.3. Техника "Синтетического Моста" (Synthetic Module Bridge)Просто обновить карту импортов недостаточно. Модули с префиксом app: не существуют физически как файлы. Они должны быть созданы программно в момент инициализации приложения. Это критически важный шаг, так как React обычно распространяется в форматах UMD или CJS, которые не регистрируются в SystemJS автоматически.7В файле инициализации ядра (src/system/bootstrap.ts) мы реализуем логику "Моста". Мы берем объекты библиотек, импортированные сборщиком ядра (Vite), и вручную регистрируем их как модули SystemJS.Реализация Bootstrap LogicTypeScriptimport * as React from 'react';
import * as ReactDOM from 'react-dom';
// ВАЖНО: Импорт рантайма требует, чтобы сборщик ядра (Vite)
// корректно разрешал этот путь (через resolve.alias).
import * as JsxRuntime from 'react/jsx-runtime';
import { System } from 'systemjs';

/**
 * Инициализирует среду выполнения плагинов, создавая
 * синтетические модули для общих зависимостей.
 */
export function bootstrapPluginRuntime() {
  console.group(' Bootstrapping Runtime');

  // 1. Регистрация React
  // Используем System.newModule для создания совместимого объекта экспорта.
  // Флаг __useDefault критичен для интероперабельности с ESM.
  System.set('app:react', System.newModule({
   ...React,
    default: React,
    __useDefault: true
  }));
  console.log('✔ Registered: app:react');

  // 2. Регистрация ReactDOM
  System.set('app:react-dom', System.newModule({
   ...ReactDOM,
    default: ReactDOM,
    __useDefault: true
  }));
  console.log('✔ Registered: app:react-dom');

  // 3. КРИТИЧЕСКОЕ ИСПРАВЛЕНИЕ: Регистрация JSX Runtime
  // Мы создаем модуль, который экспортирует jsx, jsxs и Fragment.
  // Это удовлетворяет требования сгенерированного кода _jsx(...).
  System.set('app:react/jsx-runtime', System.newModule({
   ...JsxRuntime,
    default: JsxRuntime,
    __useDefault: true
  }));
  console.log('✔ Registered: app:react/jsx-runtime');

  console.groupEnd();
}
Этот код выполняется до загрузки любых плагинов. Он создает в памяти "виртуальную файловую систему" модулей, к которой будут обращаться плагины.2.4. The Interceptor Engine: Архитектура MiddlewareПереходя к функциональной части "Суверенной Архитектуры", мы внедряем паттерн Middleware Chain (Цепочка Промежуточного ПО) в сердце системы команд ApiBus.3.1. От Событий к ИнтерсепторамКлассическая архитектура плагинов часто полагается на события (Events): on('save', callback). События хороши для реакции (логгирование, обновление UI), но они слабы для модификации поведения. События происходят после факта или параллельно ему.Для реализации сценариев "Patcher" (исправление багов) и "Encryption" (шифрование) нам нужна возможность вмешаться до выполнения действия, изменить его параметры или вовсе отменить. Паттерн Middleware, популяризированный Express.js, Koa и Redux, идеально подходит для этого.4 Он превращает поток управления в линейную (или вложенную) последовательность обработчиков.3.2. Onion Model (Модель Луковицы)Мы выбираем модель исполнения "Луковица" (Onion Architecture), используемую в Koa.js.10 В этой модели управление передается "вглубь" через функцию next(), и возвращается "наверх" после завершения вложенных вызовов.Это позволяет одному хуку выполнять логику в двух фазах:Downstream (Capture Phase): До вызова await next(). Здесь происходит валидация, подмена аргументов, блокировка.Upstream (Bubble Phase): После await next(). Здесь происходит перехват результата, обработка ошибок, замер производительности.3.3. Спецификация Типов MiddlewareCallContext: Единица СостоянияКонтекст вызова должен быть мутабельным объектом, который путешествует сквозь всю цепочку.TypeScript/**
 * Контекст перехвата вызова API.
 * Содержит всю информацию о текущей операции.
 */
export interface CallContext<TArgs extends any = any, TResult = any> {
  /** 
   * Уникальный идентификатор типа команды.
   * Например: 'editor:insert-text', 'fs:write-file'
   */
  readonly commandId: string;

  /** 
   * Аргументы вызова. 
   * Middleware может читать и ЗАМЕНЯТЬ содержимое этого массива.
   * Изменения отразятся на следующих обработчиках.
   */
  args: TArgs;
  
  /** 
   * Результат выполнения.
   * Устанавливается последним обработчиком (ядром) или
   * любым middleware, решившим прервать цепочку и вернуть ответ.
   */
  result?: TResult;

  /** 
   * Метаданные вызова для трассировки и безопасности.
   */
  readonly meta: {
    readonly id: string;         // UUID конкретного вызова
    readonly timestamp: number;  // Время начала
    readonly initiatorId: string;// ID плагина, вызвавшего команду
    depth: number;               // Глубина рекурсии (для защиты)
    isAborted: boolean;          // Флаг отмены
    [key: string]: any;          // Расширяемые поля
  };
}

/**
 * Функция передачи управления следующему звену.
 */
export type NextFn = () => Promise<void>;

/**
 * Сигнатура функции-перехватчика.
 * Асинхронна по природе.
 */
export type MiddlewareFn = (ctx: CallContext, next: NextFn) => Promise<void>;
3.4. Реализация MiddlewareRunnerКласс MiddlewareRunner отвечает за оркестрацию цепочки. Он должен поддерживать динамическую регистрацию (плагины могут загружаться и выгружаться) и эффективный матчинг команд.TypeScriptexport class MiddlewareRunner {
  // Хранилище хуков: Map<CommandPattern, Array<Hook>>
  // Мы используем плоский список для поддержки glob-паттернов
  private middlewares: Array<{ 
    pattern: RegExp, 
    fn: MiddlewareFn, 
    priority: number,
    pluginId: string 
  }> =;

  /**
   * Регистрация нового перехватчика.
   */
  register(pattern: string, fn: MiddlewareFn, priority: number, pluginId: string) {
    // Преобразование glob-паттерна 'editor:*' в RegExp /^editor:.*$/
    const regex = new RegExp('^' + pattern.replace(/\*/g, '.*') + '$');
    
    this.middlewares.push({ pattern: regex, fn, priority, pluginId });
    
    // Сортировка для детерминированного порядка выполнения
    // Высокий приоритет (HIGH) -> Низкий (LOW)
    this.middlewares.sort((a, b) => b.priority - a.priority);

    // Возврат функции отписки (Disposable)
    return () => {
      this.middlewares = this.middlewares.filter(m => m.fn!== fn);
    };
  }

  /**
   * Исполнение пайплайна для конкретной команды.
   */
  async run(commandId: string, args: any, finalHandler: (...args: any) => Promise<any>): Promise<any> {
    // 1. Фильтрация: находим все middleware, применимые к commandId
    const chain = this.middlewares
     .filter(m => m.pattern.test(commandId))
     .map(m => m.fn);

    // 2. Инициализация контекста
    const context: CallContext = {
      commandId,
      args,
      meta: { 
        id: crypto.randomUUID(), 
        timestamp: Date.now(), 
        initiatorId: 'system', // TODO: пробрасывать реальный контекст
        depth: 0,
        isAborted: false
      }
    };

    // 3. Рекурсивный диспетчер (Onion Model)
    const dispatch = async (index: number): Promise<void> => {
      // Если цепочка пройдена, вызываем оригинальный хендлер ядра
      if (index === chain.length) {
        context.result = await finalHandler(...context.args);
        return;
      }

      const middleware = chain[index];
      
      // Вызываем middleware, передавая ему next(), который замыкает index + 1
      await middleware(context, async () => {
        if (context.meta.isAborted) return; // Прерывание цепочки
        await dispatch(index + 1);
      });
    };

    // 4. Запуск
    await dispatch(0);
    
    return context.result;
  }
}
3.5. Система Приоритетов (Weights & Priorities)Порядок выполнения middleware критически важен. "Patcher" (исправление бага) должен сработать раньше, чем "Encryption", а "Logging" — позже всех (или раньше всех, но в фазе Upstream).11Мы вводим числовую шкалу приоритетов с именованными константами для улучшения читаемости.КонстантаВесНазначениеПример использованияCRITICAL1000Системные патчи, безопасность, Hotfixes.Исправление бага в fs:write. Блокировка доступа.HIGH500Трансформация данных, препроцессинг.Шифрование, транслитерация, автокоррекция.NORMAL100Стандартная бизнес-логика.Обычные плагины.LOW0Пост-процессинг, аналитика.Логирование, обновление UI статуса.Логика разрешения конфликтов: Если два хука имеют одинаковый вес, они выполняются в порядке их регистрации (First-Come, First-Served). Это стандартное поведение для Array.sort() в JS (stable sort).3.6. Безопасность: Защита от Рекурсии (Safety Nets)Одна из главных угроз в системах перехвата — бесконечная рекурсия.Сценарий: Плагин перехватывает editor:save. Внутри своей логики он вызывает api.save(), чтобы сохранить резервную копию. Этот вызов снова попадает в тот же перехватчик. Цикл замыкается, стек переполняется, браузер зависает.12Для предотвращения этого мы реализуем механизм Distributed Loop Detection на основе метаданных контекста.Алгоритм защиты:При каждом вызове API мы проверяем, инициирован ли он внутри другого хука.Если да, мы инкрементируем счетчик depth в meta.Если depth превышает порог (например, 10 или 16), ApiBus выбрасывает исключение RecursionLimitExceededError и прерывает выполнение.14TypeScript// Внутри ApiBus.execute
async execute(commandId: string, args: any, parentContext?: CallContext) {
  const currentDepth = parentContext? parentContext.meta.depth + 1 : 0;
  
  if (currentDepth > 16) {
    console.error(`Infinite loop detected in command '${commandId}'`);
    throw new Error('Recursion Limit Exceeded');
  }
  //...
}
Для корректной работы этого механизма необходимо, чтобы ApiBus умел принимать опциональный parentContext. Плагины, вызывающие API внутри хуков, должны (явно или неявно) передавать этот контекст. В идеале, ApiBus должен использовать AsyncLocalStorage (если доступен в среде) или передавать контекст через аргументы.4. Обновленная Поверхность API (API Surface)Код плагина должен быть выразительным. Мы отказываемся от сырого register в пользу семантического API, вдохновленного лучшими практиками.164.1. Пространство Имен hooksМы предлагаем разделить API на три метода, отражающих намерение разработчика, хотя под капотом все они используют intercept.TypeScriptexport interface HooksAPI {
  /**
   * Перехват с полным контролем (Interceptor).
   * Наиболее мощный метод. Позволяет вызывать next(), не вызывать его,
   * вызывать его несколько раз (осторожно!), оборачивать в try/catch.
   */
  intercept(pattern: string, handler: MiddlewareFn, options?: HookOptions): void;

  /**
   * Выполнить действие ПЕРЕД командой (Pre-hook).
   * Синтаксический сахар для intercept с высоким приоритетом.
   * next() вызывается автоматически после завершения функции.
   */
  before(pattern: string, handler: (ctx: CallContext) => Promise<void> | void): void;

  /**
   * Выполнить действие ПОСЛЕ команды (Post-hook).
   * Синтаксический сахар для intercept с ожиданием next().
   */
  after(pattern: string, handler: (ctx: CallContext) => Promise<void> | void): void;
  
  /**
   * Полная замена обработчика (Replacement).
   * next() НЕ вызывается. Используется для патчинга.
   */
  replace(pattern: string, handler: (ctx: CallContext) => Promise<any>): void;
}

export interface HookOptions {
  priority?: number; // По умолчанию NORMAL (100)
}
4.2. Примеры Использования (Use Cases)4.2.1. The Patcher (Исправление бага в ядре)Задача: В fs-manager обнаружен баг: при записи файла путь не нормализуется, что приводит к дубликатам.Решение: Плагин-патч перехватывает вызов и исправляет аргументы.TypeScript// patch-fs-bug.ts
export function activate(ctx: PluginContext) {
  // Используем intercept для точного контроля
  ctx.api.hooks.intercept('fs:write', async (call, next) => {
    const [path, content] = call.args;
    
    // ПАТЧ: Нормализуем путь перед передачей в ядро
    const fixedPath = path.replace(/\\/g, '/').trim();
    
    // Подменяем аргументы в контексте
    call.args = fixedPath;
    
    // Передаем управление дальше (оригинальному, но теперь безопасному хендлеру)
    await next();
    
    console.log(`[Patcher] Fixed path: ${path} -> ${fixedPath}`);
  }, { priority: ctx.api.constants.Priority.CRITICAL }); // Критический приоритет!
}
4.2.2. The Encryption Plugin (Шифрование)Задача: Прозрачно шифровать заметки при сохранении и расшифровывать при чтении.TypeScript// crypto-plugin.ts
export function activate(ctx: PluginContext) {
  const { hooks, constants } = ctx.api;

  // 1. Запись: Шифруем контент ДО попадания в FS
  hooks.intercept('fs:write', async (call, next) => {
    const content = call.args;
    if (typeof content === 'string') {
      call.args = encrypt(content); // Мутация аргументов
    }
    await next();
  }, { priority: constants.Priority.HIGH });

  // 2. Чтение: Расшифровываем результат ПОСЛЕ получения из FS
  hooks.intercept('fs:read', async (call, next) => {
    // Сначала даем ядру прочитать файл (await next)
    await next();
    
    // Теперь, когда оригинальная функция отработала, у нас есть result
    if (call.result && typeof call.result === 'string') {
      try {
        call.result = decrypt(call.result); // Мутация результата
      } catch (e) {
        // Ошибка расшифровки (возможно, файл не зашифрован)
        console.warn('Decryption failed', e);
      }
    }
  }, { priority: constants.Priority.HIGH });
}
5. Unsafe Context: Режим Бога (God Mode)Middleware дает контроль над потоком данных, но не дает доступа к состоянию UI и внутренним объектам. Для этого мы внедряем концепцию Unsafe Context.5.1. Принцип ИзоляцииМы разделяем API на два объекта:ctx.api: Стабильный, документированный фасад. Безопасен для использования.ctx.unsafe: "Сырой" доступ к внутренностям. Нестабилен (может сломаться при обновлении ядра), но дает неограниченную власть.5.2. Спецификация UnsafeContextTypeScriptexport interface UnsafeContext {
  /**
   * Прямой доступ к инстансу приложения (Root Store / DI Container).
   * Позволяет получить доступ к Router, SettingsService, ThemeService.
   */
  readonly app: any;

  /**
   * Глобальный объект Window.
   * Необходим для доступа к DOM (document) и Electron IPC (window.electron).
   */
  readonly window: Window;

  /**
   * Получить активный экземпляр редактора CodeMirror 6.
   * CM6 не хранит инстанс глобально, поэтому нужен хелпер.
   * @returns EditorView или null, если редактор не активен.
   */
  getActiveEditorView(): any; // Возвращает EditorView
}
5.3. Реализация доступа к CodeMirror 6CodeMirror 6 архитектурно отличается от версии 5. У него нет глобального объекта CodeMirror. Состояние (EditorState) и представление (EditorView) инкапсулированы.Чтобы предоставить плагинам доступ к EditorView, ядро должно реализовать механизм обнаружения (Lookup). EditorView в CM6 привязывается к DOM-элементу через свойство, которое обычно минифицируется или скрыто, но доступно через публичное поле cmView (в dev-режиме) или через поиск по DOM.Самый надежный способ, который мы реализуем в ядре:Найти DOM-элемент контейнера редактора, используя наш стабильный CSS-селектор: .nh-editor-active.cm-content.Использовать внутреннее свойство CM6, которое линкует DOM элемент с инстансом View. Обычно это domElement.cmView.view.TypeScript// Внутри UnsafeContextImpl
getActiveEditorView() {
  const dom = document.querySelector('.nh-editor-active.cm-content');
  if (dom && (dom as any).cmView) {
    return (dom as any).cmView.view;
  }
  return null;
}
Важное замечание о Dual Package Hazard:Если плагин использует unsafe.getActiveEditorView(), он получит объект класса EditorView. Если плагин захочет проверить view instanceof EditorView, или создать транзакцию view.dispatch(...), он должен использовать тот же самый класс EditorView, что и ядро.Если плагин импортирует @codemirror/view из своего node_modules, это будет другой класс. Проверка instanceof вернет false.Решение: Плагины обязаны декларировать @codemirror/* как peerDependencies и исключать их из сборки (см. раздел 2.4). SystemJS должен мапить @codemirror/view на экземпляр ядра.6. DevTools: Отладка НевидимогоВнедрение сложной системы хуков делает поток управления неявным.
